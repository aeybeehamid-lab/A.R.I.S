Product Requirements Document

A.R.I.S

Adaptive Responsive Intelligent System — a multimodal AI desktop operating layer
Author: Abdulhamid Last Updated: July 21, 2026 Phase 1 — Core Complete

1.Executive Summary

A.R.I.S (Adaptive Responsive Intelligent System) is a multimodal AI desktop operating layer — a system that sits on top of a user's computer and lets them interact with it through natural, human-native input: hand gestures, vision, and eventually voice, instead of only a mouse and keyboard.

Think of it as a personal "co-pilot" layer for the desktop: it watches (via camera), understands intent (via an orchestrator and reasoning engine), and acts (by controlling applications, executing tasks, or assisting decisions) — similar in spirit to Jarvis from Iron Man, but built incrementally, starting from real, working computer vision rather than a hypothetical AI assistant.

2.Problem Statement

Modern computer interaction is still fundamentally mouse-and-keyboard-bound, despite huge advances in AI, computer vision, and natural language understanding. This creates friction in several ways:

  • Certain tasks (media control, presentation navigation, quick app switching, accessibility use cases) are naturally suited to gesture or voice, but still require reaching for a physical input device.
  • AI assistants today are largely reactive text boxes (chatbots) — they don't perceive the user's environment or physical actions, and they don't act on the user's behalf inside the OS.
  • There is no unified, personal, extensible "intelligence layer" that combines perception (seeing what the user does), reasoning (understanding what they want), and action (doing it) on a normal desktop computer, built and owned by an individual rather than a large platform.

A.R.I.S aims to close this gap — starting narrow (hand gesture recognition) and expanding toward a full perceptual, reasoning, and action-taking system.

3.Vision

A.R.I.S will eventually be a layered system where:

  1. A Perception Layer watches the user (hands, screen content, eventually voice) and converts raw input (camera frames, audio, OCR'd screen text) into structured signals.
  2. An Orchestrator takes those signals and decides what they mean and what should happen next — routing "intent" to the correct handler.
  3. A Co-Founder Brain acts as a reasoning/decision-making core — using an LLM (Claude API) to interpret ambiguous intent, hold context, and make judgment calls the way a human collaborator would.
  4. A Jarvis Engine executes the decided action — controlling the OS, launching apps, simulating input, or responding to the user directly.

The long-term goal is a system that feels like working alongside a capable assistant who can see what you're doing and act on your behalf, not just answer questions in a chat window.

4.Current Status

Phase 1's core is functionally complete. What exists today:
  • A working real-time hand-tracking pipeline built in Python using OpenCV (camera capture) and MediaPipe (hand landmark detection).
  • The pipeline captures live webcam video, detects up to two hands per frame, extracts all 21 landmark points per hand (in pixel coordinates), and renders a live skeletal overlay on screen.
  • Per-finger up/down state detection across all five fingers, using y-coordinate comparison for four fingers and x-coordinate comparison for the thumb.
  • Named gesture classification (Fist, Open Palm, Pointing, Peace Sign, Thumbs Up) mapped from finger-state patterns, with an Unknown fallback for unrecognized poses.
  • Debouncing logic so a held gesture fires a single event rather than repeating every frame.
  • Project is version-controlled on GitHub with a clean, incremental commit history, a .gitignore excluding environment files, and a requirements.txt for reproducible setup.
  • Environment: Python 3.11 (chosen specifically for MediaPipe compatibility — newer Python versions such as 3.13 are not yet supported by MediaPipe), managed via a project-local virtual environment (.venv), developed in VS Code.

Not yet built: action dispatch (mapping gestures to real system actions), dynamic/motion-based gestures, the orchestrator, the co-founder brain (Claude API integration), and the Jarvis engine.

5.Phased Roadmap

Core CompletePhase 1 — Perception: Hand Tracking & Gesture Recognition

  • Real-time hand detection and landmark extraction — done
  • Rule-based static gesture classification (fist, open palm, pointing, peace sign, thumbs up) using position comparisons between landmarks — done
  • Gesture debouncing/state management so one physical gesture triggers one detected event, not a flood of repeated triggers — done
  • Remaining for full Phase 1 close-out: broader gesture set, dynamic/motion-based gestures (stretch goal, may shift to Phase 1.5 or fold into Phase 2 tooling)
Milestone: the system reliably detects 3–5 distinct static hand gestures in real time from a live webcam feed. — Achieved.

PlannedPhase 2 — Action Dispatch

  • Map each recognized gesture to a real system action (e.g. open an application, simulate a keypress, trigger a script) using tools such as pyautogui, keyboard, or pynput
  • Build a simple, extensible "gesture → action" configuration so new mappings can be added without rewriting core logic
Milestone: performing a gesture in front of the camera visibly and reliably triggers a real action on the desktop.

PlannedPhase 3 — Orchestrator

  • Introduce a central coordinating layer that can accept signals from multiple input sources (not just hand gestures — eventually voice, screen content via OCR, etc.)
  • Decide which handler/module should respond to a given signal
  • Establish the internal architecture/message format that later modules (brain, Jarvis engine) will plug into

PlannedPhase 4 — Co-Founder Brain

  • Integrate the Claude API as a reasoning core that can interpret ambiguous or complex intent, hold conversational/task context, and make judgment calls
  • Allow the system to go beyond fixed gesture→action mappings into more flexible, context-aware behavior

PlannedPhase 5 — Jarvis Engine

  • Full action-execution layer capable of controlling applications, retrieving information, and carrying out multi-step tasks on the user's behalf
  • Integration point for perception (Phase 1–3) and reasoning (Phase 4) to produce real, useful autonomous or semi-autonomous behavior

7.Success Metrics (Phase 1)

  • Hand detection runs in real time (no perceptible lag) on standard consumer webcam hardware
  • At least 3–5 distinct gestures are classified reliably and repeatably
  • False-positive gesture triggers are rare enough not to disrupt normal use
  • Codebase is clean, documented, and committed incrementally with a clear Git history

8.Risks & Open Questions

  • Scope creep risk: the gap between "detect a gesture" and "full Jarvis-like assistant" is large. Each phase needs its own realistic, scoped definition of done rather than chasing the end vision prematurely.
  • Dynamic gesture complexity: static gestures (fist, palm, etc.) are tractable with rule-based logic; motion-based gestures (swipes, circles) will likely require a lightweight ML classifier rather than pure geometry — a decision to revisit later in Phase 1.
  • Cross-platform considerations: current development is Windows-first; action dispatch (Phase 2) will need OS-specific handling if ARIS is intended to run beyond Windows eventually.
  • Performance boundaries: as more perception sources are added (OCR, voice), resource usage and latency will need active management to keep the system feeling responsive.

9.Non-Goals (For Now)

  • ARIS is not currently intended to be a cloud service or multi-user product — it is a personal system, built and used by its creator, at least through the phases outlined above.
  • Full autonomous computer control (Phase 5+) is an eventual goal, not a near-term one — early phases intentionally keep the human in the loop.

10.Appendix: Key Terms

  • Landmark — a single tracked point on a detected hand (21 per hand), given as normalized or pixel (x, y, z) coordinates.
  • Gesture classification — the process of interpreting raw landmark positions as a named, meaningful gesture.
  • Orchestrator — the internal routing layer deciding what should happen in response to a given input signal.
  • Debouncing — logic to ensure a continuous physical gesture registers as a single discrete event rather than firing repeatedly every frame.
